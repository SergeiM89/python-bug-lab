# Python API Lab

Python 3.14 / FastAPI. Без БД и внешних сервисов.

- Dockerfile, порт 8000; readiness: `GET /health`.
- Запуск: `python -m uvicorn app:app --host 0.0.0.0 --port 8000 --access-log`.
- Tests в контейнере: `python -m pytest -p no:cacheprovider tests`.
- UI: `GET /`. Корректный запрос: `POST /api/greet` с `{"name":"Ada"}` → 200.
- После исправления неполный запрос `POST /api/greet` с `{}` должен получать 422
  с понятным сообщением в `detail`, а не 500.
- Runtime stdout/stderr и access-log uvicorn содержат диагностику.

## Запуск в Docker

```sh
docker build -t python-bug-lab .
docker run --rm -p 127.0.0.1:8001:8000 python-bug-lab
```

Откройте http://localhost:8001 и нажмите «Запрос без имени»: исходная версия
вернёт 500. Страница покажет `KeyError: 'name'` и полный traceback из ответа
backend. Тот же traceback Uvicorn пишет в stdout/stderr, откуда его собирает
Bug Investigator. Корректный запрос должен по-прежнему возвращать 200.

После исправления тот же запрос должен возвращать 422 и сообщение вроде
«Запрос отклонён: поле name обязательно и должно быть непустой строкой», без
необработанного исключения и traceback. Внешний вид результата меняется с
«Ошибка backend» на «Запрос отклонён» по реальному HTTP-статусу.

В учебном стенде включён `debug=True`, чтобы преподаватель видел диагностику
необработанного исключения прямо на странице. Обработанные HTTP-ошибки 422
продолжают возвращаться как JSON.

Регрессионные тесты: `docker run --rm python-bug-lab python -m pytest -p no:cacheprovider tests`.
В исходной версии тест валидации намеренно падает: цель задания — исправить приложение.

## Проверка агентом

URL: https://github.com/SergeiM89/python-bug-lab. Ветка по умолчанию `main`
содержит API-дефект; `demo/api` — тот же исходный сценарий. Ветка `demo/build`
содержит два дефекта: неверный `COPY missing/requirements.txt .` в Dockerfile и
необработанный запрос без имени. После восстановления сборки API-дефект остаётся
задачей для исправления; автоматические тесты могут обнаружить его ещё до ручной
проверки. `baseline/healthy` — исправный контрольный вариант с 422 и правильным сообщением.
Для повторения используйте новый сеанс с выбранной веткой.

Исправления сначала выполняются и проверяются локально. Публикация PR — отдельное
действие после проверки результата и подключения GitHub с правом записи.
